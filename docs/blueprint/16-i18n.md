# Internationalisation, from the first line

> **Founder, 2026-08-25:** *"even though the first version is only english, we will not make the
> same mistake we did on FlowForge, use i18n from the get go… creating a file and the other
> languages just works."*

**English is the only language in v1.** This document exists so that the second language is a file,
not a project.

---

## 1 · The one rule

> **No user-facing string literal appears in code. Every string comes from a catalogue, by key.**

That is the whole discipline, and it is worth stating as one line because it is the only part that
has to hold on **every commit from the first**. Everything else in this document is mechanics.

The reason it must start on day one rather than be retrofitted: a retrofit has to find every string
in a finished product, and the ones it misses are exactly the ones nobody looks at — errors, empty
states, the fatal screen. Those are the screens a player only sees when something has already gone
wrong, which is the worst moment to meet a language you cannot read.

### 1.1 · The lint that makes it reviewable

A rule nobody can check is a convention, not a rule. **A string literal reaching a render path is a
build failure, not a review comment.**

The check: no string literal may be passed to a rendering or formatting call outside the catalogue
package. Allowed literals are keys, format verbs, and strings that are not language — a token name, a
provider ID, a file path, a SQL fragment. The allow-list is small and explicit, and anything that
wants onto it needs a reason in the diff.

`fft-api-designer` owns the exact shape; the spine's requirement is that **the check exists, runs in
CI, and fails the build** rather than producing a warning nobody reads.

---

## 2 · The library, and why

**`golang.org/x/text`.** It is already in the dependency set, it is the Go project's own
internationalisation work, and it carries the four things a naive catalogue does not: plural rules
(CLDR), locale-aware number and currency formatting, collation, and the `language.Matcher`
negotiation that decides what to show a player whose locale you do not have.

The catalogue itself is `golang.org/x/text/message` with per-language files. Adding `pt-BR` is
adding one file and one `//go:generate` run — **no code change**, which is the founder's test.

Rejected, with reasons: hand-rolled `map[string]string` (no plurals, no CLDR, and it always becomes
one of the others eventually); `go-i18n` (fine, but a second dependency for what `x/text` already
does); and gettext-family tooling (a toolchain to install, for a benefit Go's own library provides).

## 3 · What naive i18n misses, and what Zerado does about each

The interesting part. A catalogue of strings is the easy half.

### 3.1 · Terminal cell width — the one most likely to be missed, and the most damaging here

**This is the TUI-specific failure, and it interacts directly with every column budget in this
bundle.** `é` is one rune and one cell; `한` is one rune and **two** cells; a combining accent is a
rune and **zero** cells. A layout that measures a string with `len()` — or even with
`utf8.RuneCountInString()` — is wrong the moment a title is not ASCII, and it is wrong *today*,
before any translation, because **game titles are already not ASCII**: *Pokémon*, *Ōkami*,
*NieR:Automata*.

The rule, and it is the same one the glyph-width work already established
([`02-composition.md`](./02-composition.md) §2.2.1): **every width measurement is
`east_asian_width`-aware, and Ambiguous counts as one cell.** Never `len()`. Never rune count.

Three consequences that must not be forgotten:

- **Truncation budgets subtract the *measured* width of the ellipsis**, not `1`
  ([`../design/01-design-system.md`](../design/01-design-system.md) §1.2 rule 3).
- **A single rune can exceed a one-cell column.** Any field of width 1 is unsafe for arbitrary text.
- **Padding is computed from measured width**, so a right-aligned column stays aligned when a title
  contains CJK.

### 3.2 · Currency, and why it is not optional

The budget feature is **money, in the player's own currency**. `$15` is not a fallback for
`R$ 15,00` — the symbol, the separator, the decimal mark and the symbol's *position* all differ, and
getting them wrong makes a financial claim look untrustworthy in exactly the feature whose value is
trust. `x/text/currency` + `x/text/number`, driven by the player's locale, never a format string.

### 3.3 · Plurals

`1 game` / `247 games` is the easy case English teaches. Portuguese, Russian and Arabic each need
more forms, and a catalogue that stores one string per key cannot express them. CLDR plural rules,
via `x/text/message` — and **the English catalogue uses them too**, so the mechanism is exercised
from day one rather than discovered when the second language arrives.

### 3.4 · Collation

Sorting titles is `x/text/collate` under the player's locale, not `sort.Strings`. Byte order puts
*Ōkami* after *Zelda* and every accented title in the wrong place — visible **today**, in English,
which is what makes this worth doing now.

### 3.5 · Dates

*"3 days ago"* is a formatting decision with plural rules and locale-specific phrasing. The
[`07-offline-contract.md`](./07-offline-contract.md) §4.1 age rule — *ages are said the way people
say them* — is a **catalogue** concern, not a `fmt.Sprintf`.

## 4 · `zerado` and `sinopse` stay Portuguese

**Ratified brand vocabulary, not untranslated strings.**

The name is Portuguese and the product is named after the act; `sinopse` is kept and explained once,
per the ratified language decision. **A future translator must not "fix" them**, and a future
reviewer must not file them as a bug — so the English catalogue carries them as deliberate
Portuguese with a translator note, and every other catalogue inherits the same note.

This is the one place where the catalogue needs to carry *intent*, not just text.

---

## 5 · Locale: where it comes from, and how a player overrides it

| Order | Source |
|---|---|
| 1 | `ZERADO_LANG`, if set — the explicit override, and it wins |
| 2 | The `language` setting in `Z-09 Settings`, if the player has chosen one |
| 3 | `LC_ALL` → `LC_MESSAGES` → `LANG`, the POSIX order the player's shell already uses |
| 4 | `en` |

Negotiation is `language.Matcher`, so `pt-PT` falls back to `pt-BR` before it falls back to English —
which is the behaviour a Portuguese speaker expects and a naive exact-match lookup gets wrong.

**Formatting locale and message locale are separate.** A player may want English text and their own
currency and date format; that combination is common and the settings model should permit it.

## 6 · What Phase 1 actually builds

| Built | Not built |
|---|---|
| The catalogue, with English as its only language | Any second language |
| The no-literals lint, in CI, failing the build | A translation workflow or a translator-facing tool |
| Width-aware measurement everywhere | — |
| Locale-aware number, currency, date and collation | — |
| Plural rules, exercised by the English catalogue | — |

**The acceptance test is one sentence:** adding `pt-BR` is adding one file. If it needs a code
change, this failed — and the failure is measurable rather than a matter of opinion.
